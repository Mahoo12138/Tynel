# Tynel 学习笔记写作指南

每次新写或修改笔记，先读本页。笔记的任务是带读者做完一次实验，并理解其中的关键选择；规格、术语表和测试报告各有自己的位置。

## 先确定这一篇要做成什么

用一句话写下目标，例如“让手写加法 NIR 经过 Go 后端生成 exe”。选一个贯穿全文的小程序，读者每读完一节，都应离这个目标近一步。另开一个知识专题才能讲清楚的内容，移到参考资料或留待真正需要它的阶段。

读者会写简单的 C 程序，知道函数、变量和调用。可以带他看少量 Go 内部代码，但每段只解释眼前要用的动作，避免同时补齐整套语言或编译原理。

## 围绕实验推进

先给具体输入和想看到的结果，尽早让程序跑起来。接着沿输入流经的代码解释关键步骤，再改一个条件或输入，观察行为是否符合预期。最后收束到“已经得到什么、接下来还缺什么”。这是思路，不是每篇必须套用的标题模板。

命令与输出紧挨着写。注明工作目录、准备入口、输入文件和预期退出状态；完整日志放验证记录。代码片段要区分可运行源码、真实摘录和省略字段的示意。图用于展示数据或执行路径，一张图只回答一个问题。

## 只解释此刻有用的概念

引入术语之前，先让读者遇到它要解决的问题。能用一句解释继续实验，就先讲到这里。例如类型查询需要说明“answer 没写类型，却能推断为 number”；不必因此展开检查器池、全部类型系统和内存布局。

每段背景都问一句：删掉它，读者还能完成并理解眼前的步骤吗？能，就删掉、后移或给一个可选链接。尤其不要在第一篇同时讲 AST、SSA、浮点位模式、ABI 和 GC。

## 正面说明做法，集中交代边界

先写“输入交给谁、它生成什么、结果怎样观察”。影响命令或结果的限制就地说明；其余限制在结尾用一小段归拢。一个边界解释一次即可，不用反复写“不意味着”“不能据此推断”。精确性靠范围、代码和证据，不靠防御性语气。

## 给文字留出停顿

一段解决一个问题。长句拆开，定义不要连发，标题写动作或具体问题。保留必要的例子与推导，不把删背景变成只剩命令清单。少用加粗、概念罗列和层层小标题；不写“本文只要求”“接下来我们将”等空转句。

第一人称只用于真实的选择、尝试和观察。不要编造踩坑、对话、当时的想法，也不要把改名、整理 Git、用户编辑意见写进实验正文。

## 交稿前实际检查

从头只读正文，确认没有依赖侧栏或术语表才能继续的跳跃；逐段检查是否仍在推进同一个实验。运行文中的命令，核对 stdout、诊断、路径、版本与源码片段。事实引用放在相关实现处，延伸阅读放文末，避免每句话挂一串资料。

正文只保留关键观察。完整回归数量、失败过程、平台范围与内容指纹写入验证记录；未运行的步骤明确标为预期。源码、笔记、指南和验证记录随对应阶段一起提交，文章头部 `experiment_tag` 必须指向该状态。参考表和指南不另设阶段。
