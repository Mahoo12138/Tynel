<a id="control-flow"></a>
## 条件与控制流

boolean 是 true/false 两种值的类型；truthiness 是其他类型的值按某套规则转换为条件的过程。两者不同。Tynel 的 `stage/04-control-flow` 只接受 boolean 条件，不接受 `if (number)` 或 `!number`。

CFG（Control Flow Graph，控制流图）记录执行可以从哪个位置转向哪个位置。基本块描述连续的低层执行片段；源码 `{ ... }` 的词法块限制名称可见范围，二者不一一对应。分支内变量只在该范围可见，与运行时数据是否复制没有必然关系。

“所有路径返回”是在问每条能走到的函数出口是否都有结果，不是计数 return。当前结构检查不利用常量条件排除分支。具体问题、实例与实现见 [笔记 04](../notes/04-control-flow.md) 和 [ADR-016](../adr/016-boolean-control-flow.md)。这张表随阶段保存，不另建标签。

<a id="versions"></a>
## 版本与复现：commit、tag、worktree

**commit（提交）**保存一组已纳入 Git 的文件快照。未提交的源码不会因为 tag 指向 HEAD 就自动被保存。**annotated tag（附注标签）**为某个提交起一个可读名字，并附带说明；Tynel 用 `stage/NN-topic` 标识可重跑的实验节点，而不是宣称完成整个 M0/M1。标签打错或实验补修时新建节点，不强制移动旧标签。[Git tag 文档](https://git-scm.com/docs/git-tag)

**worktree（工作树）**让同一仓库同时检出多个提交到不同目录。做旧实验优先使用它，不在当前开发目录直接切分支，不执行清理命令丢弃正在做的工作。源码 tag、工具链 lock、测试输入和运行环境共同构成复现条件；tag 本身不包含被忽略的 SDK 或二进制。具体命令见 [复现指南](../reproducing.md)。

## 1. 先分清：哪些是通用概念，哪些只是项目里的名字

这些词放在一句进度汇报里，看起来像一组必须同时掌握的编译器术语。实际上，它们来自不同层次：

| 名称 | 先用一句话理解 | 属于哪一类 |
|---|---|---|
| `probe.gc/1` | “我要使用第 1 版 GC 实验能力”的标签 | Tynel 自己定义的输入标记 |
| ADR | 记录某项技术决定，以及为什么这样决定的文档 | 通用的软件设计记录方式 |
| `T09` | 当前规格中的第 09 号任务 | Tynel 项目管理编号 |
| ABI 探针 | 检查编译后的代码与辅助库能否按约定配合的实验 | 通用概念加本项目的具体测试 |

所以，“完成了 T09 的 GC／ABI 探针，并写入 ADR-013”，可以读成：

> 按第 09 号任务的安排，我们做了一组小实验：一组检查对象在垃圾回收后是否仍然正确，另一组检查错误的辅助库是否会被拒绝。采用这种实验方案的理由，记录在编号 013 的技术决策文档里。

这句话本身**不表示 TypeScript 对象语法已经全部实现，也不表示整个阶段已经完成**。下面分别解释它的各个部分。项目中的对应定义见规格任务表和 ADR-013。[^task][^adr-local]

<a id="probes"></a>
## 2. 探针是什么？为什么不直接开发完整功能？

### 2.1 探针就是围绕一个问题设计的小实验

这里的 **probe，探针**，不是特殊硬件，也不是必须安装的调试插件。它指一段刻意构造的小程序、一组测试输入或一段检查脚本，用于验证某个具体假设。

例如，普通加法例子已经能输出 `42`。接下来还想知道：

> 如果程序创建一个对象，让它经过几次垃圾回收，再读取字段，值还对不对？

不用先实现 TypeScript 的全部对象语法，就可以用一份固定的结构体做实验。把问题缩小，出错时也更容易判断是分配、引用、字段访问还是链接出了问题。

项目目前用 **IR（Intermediate Representation，中间表示）** 描述实验程序。可以把它理解成编译器内部的一份结构化程序说明，记录“创建对象”“调用函数”“读取字段”等操作。固定 GC 探针的输入是专门构造的 NIR JSON，`NIR` 是 Tynel 对这层原生编译中间表示的称呼；不要把探针的来源与后续阶段的 `.ts → NIR` 混为一谈。[^ir][^generator]

### 2.2 smoke、断言和夹具也没有那么神秘

脚本名里的 **smoke test，冒烟测试**，在这里表示先验证关键路径能否工作的一组基础检查，不是完整正确性证明。

**断言（assertion）** 是写清楚“结果必须满足什么条件”。例如“输出必须为 42”“两个引用必须指向同一个对象”，不满足就判定实验失败。

**测试夹具（fixture）** 是专门准备的输入或依赖。它可以是正确的对象定义，也可以是故意写错字段顺序的辅助库。后者不是待修复的业务代码，而是用来检查编译器能否识别错误。

理解这些词，可以先用三句普通话替代它们：**做一个小实验，准备好输入，规定什么结果算通过。**

<a id="gc"></a>
## 3. GC 探针：不是“让 GC 删掉对象”，而是“别删错对象”

### 3.1 GC 负责什么

先补两个背景词：**运行时（runtime）**是与生成程序一起工作的基础代码，负责内存管理等支持任务；**堆（heap）**是可以存放跨函数调用存活的数据的一类内存区域。比如函数创建了一个对象并返回它，调用者之后还要继续使用它。

**GC** 是 Garbage Collection，垃圾回收。在具有垃圾回收机制的语言里，运行时会识别哪些堆对象仍能被程序通过有效引用访问，并据此回收不再需要保留的内存。Go 的 GC 指南把对象之间的引用关系作为理解这一过程的基础。[^gc-guide]

学过 C 的话，可以对比自己调用 `malloc` 和 `free` 时的责任：太早释放，后续访问就不安全；一直不释放，不再需要的内存就可能被长期占着。使用 GC 后，程序员通常不再逐个释放普通对象，但编译器和运行时必须正确协作。

这里的**对象**先理解为“一块带有字段的数据”，不必联想到 JavaScript 的原型或类。

**引用**在这个固定实验里就是指向对象的指针。**别名（alias）**指不同变量引用同一个对象，而不是复制出一个新对象。

### 3.2 这次只使用一种固定对象

实际的 Go 辅助包中定义了：

```go
type Node struct {
    Value float64
    Next  *Node
}
```

意思是：一个名为 `Node` 的结构体，包含一个浮点字段 `Value`，以及一个指向另一个 `Node` 的指针 `Next`。`float64` 是 64 位浮点数，`*Node` 是指针类型。[^support]

用熟悉的 C 语法解释，概念上接近：

```c
struct Node {
    double value;
    struct Node *next;
};
```

这段 C 代码只是帮助理解字段，不是 Tynel 生成的代码，也不是对两种语言 ABI 完全一致的承诺。

### 3.3 两个变量，不一定有两个对象

实验中的引用关系可以画成：

```text
root  ──┐
        ├──► 父对象：Value = 42
alias ──┘              Next ──► 子对象：Value = 7
```

`root` 与 `alias` 指向同一个父对象。因此，通过 `alias` 把 `Value` 改成 43，再从 `root` 读取，也应该得到 43。

子对象没有一个专门用于长期保存它的独立局部变量；它需要通过父对象的 `Next` 字段继续存活。这样就能检查：编译器有没有把这个字段保留为 GC 能识别的真实指针。测试程序的构造过程在 `internal/probe/gc.go`。[^generator]

所谓 **GC 根（root）**，可以先理解成运行时开始追踪引用时的起点，例如运行中的函数里仍然有效的引用和某些全局引用。这里局部变量恰好取名 `root`，这个名字本身不会产生任何特殊能力；能否被正确追踪，取决于生成代码及相应的指针信息。[^gc-guide][^liveness]

### 3.4 `42、7、43` 分别在检查什么

下面是根据真实 NIR 整理的伪代码，**不是当前可直接编译的 TypeScript、C 或 Go 源码**：

```text
root = makeNode(40)
触发一次 GC

alias = root
alias.Value = 42
linked = linkNode(root, makeNode(7))

再次触发 GC
进行深层函数调用，并在深处触发 GC

断言 root、alias、linked 都指向同一个父对象
输出 root.Value          // 42
输出 root.Next.Value     // 7

alias.Value = 43
再次触发 GC
输出 root.Value          // 43
```

第一行输出检查父对象的字段；第二行检查指针字段指向的子对象；第三行检查通过别名的修改是否反映到原对象上。身份断言还会直接比较指针，不能仅凭“两个对象字段恰好相等”就判定它们是同一个对象。[^generator][^bootstrap]

触发 GC 的辅助函数不接收这些对象作为参数，也不把它们存进全局变量。否则，辅助函数自己可能把对象保住了，实验就无法有效检查生成的调用者是否正确保留引用。[^bootstrap][^adr-local]

<a id="stack-barrier"></a>
### 3.5 深栈和写屏障为什么也会出现

**栈帧**是函数一次调用所需的一部分工作空间。Go 的运行时会管理 goroutine（一种用于执行并发任务的执行单元）的栈，并在需要时增长它。深层调用是为了让实验经过不只是简单返回的一条执行路径。[^runtime]

当前辅助代码从 `grow(128)` 开始递归，每层设置一个 1024 字节数组，在最深处执行 GC，返回时再校验数组。它用于增加栈和引用存活的验证场景，不是测量递归性能，也不代表所有栈边界都已覆盖。[^support]

另一个词是 **写屏障（write barrier）**。例如：

```text
parent.Next = child
```

这改变了对象之间的指针关系。在需要配合 GC 的时候，编译器会为这种指针写入安排相应处理；它不是“禁止写入”的屏障，也不是磁盘写入功能。Go 编译器的后端有专门的写屏障插入逻辑。[^writebarrier]

当前脚本检查生成代码中是否存在分配和写屏障调用，再运行程序验证结果。**在反汇编里找到屏障调用，不代表每次运行都实际进入那条条件分支。** 这一限制已写入 ADR。[^gc-script][^adr-local]

因此，GC 探针目前提供的是“这组固定对象的分配、引用传递、字段写入和存活路径得到验证”的证据，不是所有对象、闭包、并发情况或内存泄漏问题都已解决。

<a id="probe-gc"></a>
## 4. `probe.gc/1` 到底是什么

### 4.1 它是一段需要精确匹配的字符串

可以按命名意图这样读：

```text
probe  → 实验探针
  gc   → 这组实验围绕垃圾回收相关对象路径
  /1   → 这组实验能力的第 1 版约定
```

在实现中，它首先是一个完整的常量字符串：

```go
const ProbeGCFeature = "probe.gc/1"
```

验证器识别的是这个确定的名称，不是一个可以随意改写的路径表达式。它不是除法、Go 版本号、网络地址，也不是一个要安装的 npm 包。[^ir][^verifier]

NIR 模块通过 `features` 字段声明要使用它。例如下面是一个**模块头部片段**，省略了函数等必需内容，不能单独拿去构建：

```json
{
  "irVersion": 2,
  "semantics": "tynel.shared-core/0.1",
  "package": "main",
  "features": ["probe.gc/1"]
}
```

### 4.2 显式开启，是为了划清实验范围

在模块声明该能力后，验证器才允许 `probe_ref` 和相应的 `probe_*` 操作。`probe_ref` 是这次固定 `Node` 的可空引用；它不是 TypeScript 任意对象类型，也没有完整表达 `null` 与 `undefined` 的区别。[^ir][^adr-local]

几个操作可以直接按字面理解：`probe_new` 创建固定对象，`probe_store_value` 写入数值字段，`probe_store_next` 写入指针字段，`probe_gc` 触发 GC，`probe_assert_same` 检查两个引用是不是同一对象。

没有声明能力就使用这些操作，会被验证器拒绝；重复声明、未知能力名或错误类型，也不会因为加了一个标签就变合法。[^verifier]

这个约束称为 **feature gate，功能门控**：在输入中明确声明“我正在使用实验能力”。它是分类和检查机制，**不是安全沙箱，也不授权执行任意不可信 IR**。

另外，不声明 `probe.gc/1`，并不表示生成的程序不使用 Go runtime 或完全不涉及 GC。它只是不允许输入使用这组测试专用操作。当前普通数字程序也会保留辅助库版本锚点，这与是否允许对象探针是两项不同检查。[^adr-local]

### 4.3 为什么 `/1` 和 NIR v2 不一样

`irVersion: 2` 是整份 NIR 文件格式的版本；`probe.gc/1` 中的 `1` 是其中一项实验能力的版本。格式升级时，能力本身可以不变，两个数字没有必须相等的理由。

就像一份第 2 版实验手册，可以仍然采用第 1 版的某个实验方案。当前 v1 NIR 输入被明确拒绝，是这次格式迁移的决定，不是因为“GC 也必须升级到第 2 版”。[^adr-local][^ir]

<a id="abi"></a>
## 5. ABI：机器码之间必须遵守的约定

### 5.1 API 与 ABI 的区别

看一个 C 函数声明：

```c
double add(double a, double b);
```

它告诉源码调用者：函数叫什么、接受什么类型、返回什么。这是理解 **API（Application Programming Interface，应用编程接口）** 的一个入口。

编译成机器码之后，还要回答其他问题：参数放在哪些寄存器或栈位置？结果从哪里取？结构体字段从哪个字节偏移开始？这些属于 **ABI（Application Binary Interface，应用二进制接口）** 的约定。寄存器可以先理解成 CPU 内用于暂存数据的位置。[^abi]

假设一边把参数放在浮点寄存器，另一边却按整数寄存器读取，即使两边都把函数叫作 `add`，也不能正确配合。这是说明问题的假设情景，不是在描述当前 Tynel 的实际参数位置。

**API 关注源码怎样使用接口；ABI 关注编译后的代码怎样配合。** 重新编译时有机会重新检查类型，拿着已有目标文件去链接时，则更需要一致的二进制约定。

### 5.2 字段相同，总大小相同，布局仍然可能不同

想象两个分别编译的模块，各自认为同一份对象是下面的布局：

```c
/* 模块 A 预期 */
struct NodeA {
    double value;
    struct NodeA *next;
};

/* 模块 B 提供 */
struct NodeB {
    struct NodeB *next;
    double value;
};
```

**只为示意**，假设 double 和指针都占 8 字节、也按 8 字节对齐：

```text
              偏移 0..7        偏移 8..15
模块 A 预期   [ 数值 value ]    [ 指针 next ]
模块 B 提供   [ 指针 next  ]    [ 数值 value ]
```

这不是 C 标准保证的所有平台布局，也不是在建议把两个类型强制转换使用。它说明：即使双方都说“16 字节的对象”，也不能据此断定它们兼容。

如果一端按错误的偏移读字段，就可能把指针内容当成浮点数，或者把数值内容当成指针。对带 GC 的对象，还要确保“哪些字段是指针”的描述一致。[^abi][^liveness]

本项目确实准备了一个交换 `Next` 和 `Value` 顺序的错误 Go 类型。bridge 在生成目标程序节点之前，会检查类型来自哪个包、字段数量、名称、顺序和类型，发现错误就返回 `TY4002`，不会故意让错误程序运行后再看它是否崩溃。[^bridge][^bad-layout]

### 5.3 为什么用了 Go 后端，还需要自己检查

Go 后端能按它理解的类型生成代码，但 Tynel 仍必须正确地把自己的 IR、辅助函数和固定对象类型交给它。借用了后端，不等于前端提供的每项假设都会自动正确。

而且 Go 官方明确说明，Go 内部 ABI 不是跨版本稳定接口。因此，这个项目要保持编译器、辅助库、包产物和链接工具的配套，不能拿“都是 Go 代码”当作可以随意混用的依据。[^abi]

<a id="abi-probe"></a>
## 6. ABI 探针具体怎样检查

### 6.1 锚点：让依赖关系真实存在

进度记录里提到的 **身份锚点**，在这里是一条带版本名称、必须保留的辅助函数调用链：

```text
生成程序的 main
    → tynelProbeABI_v1()
    → probesupport.ABI_v1()
```

其中的 `ABI_v1` 函数体目前是空的，但“这个函数必须存在，并且被生成程序引用”这件事有用：它把辅助库约定体现为实际符号依赖。**符号**可以先理解成编译和链接阶段用来辨认函数或数据的名称。测试用 `go tool nm` 检查目标程序保留了对应符号。[^bootstrap][^support][^abi-script]

这不是每次调用都做一遍复杂的版本验证；函数名也没有魔法。实际保护来自调用链、编译期类型检查、构建身份检查和链接器的包一致性检查。当前的 `noinline` 标记用于防止这条实验调用被直接展开消掉，测试仍需确认最终符号存在。[^adr-local][^abi-script]

还要区分两种“身份”：GC 实验中的**对象身份**是在问两个引用是否指向同一对象；ABI 检查中的**辅助库身份**是在问程序是否使用了约定的支持组件。这两件事不能互相替代。

### 6.2 正向测试与负向测试

**正向测试**：准备一组应该正确的输入，要求成功。这里先拿同一次构建产生的匹配包归档，直接交给链接器，确认生成的程序输出 `42`。

**负向测试**：故意准备一组错误输入，要求在规定位置、以规定原因失败。这里保留主程序归档，只把辅助库替换成刻意不匹配的旧版本夹具，再直接调用链接器。[^abi-script][^bad-support]

包归档通常是 `.a` 文件，可以先理解为保存已编译包内容、供后续构建和链接使用的产物。链接器负责把所需内容组合为程序；这里不需要先掌握它的文件格式。

为什么先做正确对照？因为如果连正确库都不能链接，后面错误库“链接失败”就不能证明检查有效。测试还要检查失败原因：找不到链接器、磁盘路径错误或进程超时，都不能被当成成功识别 ABI 错配。[^abi-script]

### 6.3 当前四项检查

| 检查 | 预期 | 主要检查位置 |
|---|---|---|
| 普通数字程序保留 `ABI_v1` 符号 | 存在 | 对最终二进制进行符号检查 |
| 正确包直接链接 | 成功，程序输出 42 | 链接器与生成程序 |
| 换成旧辅助包后直接链接 | 因包指纹或相关符号不匹配而失败 | 链接器，绕过 driver 预检 |
| 换成错误字段顺序的类型 | 报 `TY4002` | bridge 的类型／布局检查 |

这里 **driver** 是组织构建步骤的驱动程序；**bridge** 是把 Tynel IR 接入 Go 编译器内部表示的转换代码。把检查位置分开，可以避免“只在外层拦住了输入，却说链接器也验证过”的误报。[^bridge][^abi-script]

既有开发记录中，旧辅助包的实际拒绝原因是：

```text
fingerprint mismatch: tynel.local/bootstrap/probesupport
```

即包指纹不匹配。**指纹**在这里表示用来核对包身份的一项记录，不是人工设置的密码；项目还使用 SHA256 计算源码内容摘要，但不能把它与 Go 包指纹当成同一种算法。实际记录证明的是这次旧包混用被拒绝，并没有独立证明所有缺失符号情形都已触发。[^progress]

### 6.4 测试通过不等于万能认证

这组 ABI 探针验证的是当前固定对象、指定辅助函数和包组合。它不是检查任意恶意二进制篡改的安全系统，也不能保证“公开类型不变，但函数行为变了”这种差异一定被识别。

它更不意味着不同 Go 版本、不同操作系统、所有对象类型和完整库生态已经可以互通。完整 ABI 身份与混用拒绝仍有后续任务。[^adr-local][^progress]

<a id="adr"></a>
## 7. ADR：把“为什么这样做”写下来

**ADR** 通常展开为 Architecture Decision Record，也常写作 Architectural Decision Record，中文可以叫**架构决策记录**。

它的用途不是再写一份规格，也不是逐天记录做了多少工作，而是保存一项重要决定的背景、选择和后果。Michael Nygard 对这种记录方式的介绍强调了短小的记录，以及背景、决定、状态和后果等内容。[^adr-origin]

对 Tynel 来说，三类文件各自回答不同问题：

| 文件 | 主要回答的问题 |
|---|---|
| `SPEC.md` | 项目要遵守什么技术规则，目标与验收条件是什么？ |
| `docs/adr/013-spec-authority-and-m1-probes.md` | 这次为什么采用固定对象探针，为什么要显式门控，有哪些暂时的限制？ |
| `docs/progress-t09.md` | 实际实现了什么，执行了哪些检查，结果是什么，还缺什么？ |

例如，“先借用手写 Go 包中的固定 `Node` 类型，不立即实现通用 TS 对象布局”，是一项值得记录的决定。它使实验可以专注于引用存活和代码生成，但代价是暂时不能据此宣称支持任意对象。这个取舍及其边界，已经写入 ADR-013。[^adr-local]

一份自己的 ADR 可以按下面这个提纲写；这是建议模板，不是要求所有项目都使用相同格式：

```text
标题与编号：决定讨论什么
状态：提议、采纳、被替代等
背景：当前要解决哪个问题
决定：这次选择怎样做
备选：还考虑过什么，为什么暂未采用
影响：得到什么，限制什么，怎样验证
相关资料：规格、实现、测试与后续任务
```

**“状态：采纳”只表示选择了这个设计，不表示代码已完成或测试已通过。** 也不意味着为了产生 `ADR-013`，仓库里一定已有 12 篇完整决策文档；编号只是用于稳定引用，不是质量或进度分数。

以后改变选择时，应留下新决定与旧决定的关系，不把过去的理由无痕改写成“我们一直如此”。

<a id="t09"></a>
## 8. T09：一个任务编号，不是一门新技术

`T09` 是当前 `SPEC.md` 第 19 节任务表中的编号。它的真实定义是：[^task]

| 项目 | 当前定义 |
|---|---|
| 编号 | T09 |
| 阶段／优先级 | M1/P0 |
| 任务 | 最小对象 GC smoke 与身份锚点原型 |
| 直接依赖 | T08 |
| 完成证据 | GC 后字段正确；锚点失配可识别 |

可以逐段翻译：

**T09**：第 09 号任务。它是引用标签，不意味着必须一口气做完前八项，才能阅读或讨论它；实际实施还要看依赖和当前基线。

**M1**：Milestone 1，第 1 个里程碑。里程碑是一组阶段目标；这里围绕 NIR 到 Go 高层 IR、再到原生执行的基础闭环。

**P0**：规格把它定义为当前里程碑的关键路径；不是“耗时 0 天”，也不是一个语言版本。P1 对应后续验收完善，P2 对应选修研究。[^task]

**依赖 T08**：应先有基本 main、包初始化和链接路径，才能在这个基础上做对象实验。

**完成证据**：不是“写了几个文件”，而是实验必须展示 GC 后的数据正确，以及指定的错配能被识别。

这次已经有固定对象实验和辅助身份检查的实现及历史执行记录，但还没有因此完成整个 M1。当前记录仍列有上游精确版本锁定、完整包导出、闭包及其他边界待补。后续 `T39` 还要研究更完整的 ABI 身份与混用拒绝。[^progress][^task]

旧计划曾重排过编号，所以读 `T09` 时，应以当前根目录 `SPEC.md` 为准，不能从更早附件中找一个同号任务就认为是同一件事。

<a id="identifiers"></a>
## 9. 这些数字不是同一个版本，也不是同一种编号

以下值来自当前代码与锁文件：[^ir][^lock][^adr-local]

| 写法 | 编号针对什么 | 不表示什么 |
|---|---|---|
| `T09` | 一项实施任务 | 不表示语言第 9 版 |
| `M1` | 一个实施阶段 | 不表示某个文件格式 |
| `ADR-013` | 一份决策记录 | 不表示 13 项功能都已完成 |
| `irVersion: 2` | NIR 文件格式 | 不要求所有能力都升级成 `/2` |
| `probe.gc/1` | 一组实验操作的约定 | 不是 Go GC 第 1 版 |
| `tynel.probesupport/1`、`ABI_v1` | 辅助库约定与相关版本锚点 | 不是整个项目已经发布为 1.0 |
| `TY4002` | 一类诊断代码 | 不是版本号，也不是通过数量 |

因此，同一个程序同时采用 NIR v2、`probe.gc/1` 和 `ABI_v1` 是合理的。要检查的是相关接口是否配套，而不是把所有数字机械地改成相同值。

这也解释了为什么开发记录会同时出现“任务”“版本”“测试次数”和“错误码”：它们分别回答工作安排、格式约定、验证样本和失败分类，不能互相当成进度。

## 10. 怎样结合仓库继续读，必要时自己运行

最短的阅读路线是：先看本文，再看 [T09 开发记录](../progress-t09.md)，最后看 [ADR-013](../adr/013-spec-authority-and-m1-probes.md)。想了解代码如何实现，再读 [实验程序生成器](../../internal/probe/gc.go) 和 [辅助类型定义](../../experiments/bootstrap/probesupport/support.go)。

**本次只核对文档和源码，没有重跑完整编译器回归。** 既有记录写明普通与压力模式各 20 次通过，ABI 四项通过；这些是上一轮的记录，不是本文新增的测试结果，也不是所有输入的数学证明。[^progress]

需要复现时，以下是当前仓库脚本的使用方式，不是可在任意空目录直接执行的安装教程。先具备项目要求的 Windows amd64、PowerShell 7、Go 1.26.7 环境，检出 `stage/02-tsgo-query`，按复现指南准备该目录自己的 SDK。第一条会在项目内构建独立 bridge，后两条会生成测试文件与可执行产物：

```powershell
cd D:\Code\Tynel
git worktree add --detach .tynel/replays/gc stage/02-tsgo-query
cd .tynel/replays/gc
pwsh -NoProfile -File scripts/replay.ps1 -SdkSource D:\Code\Tynel\.tynel\sdk\go1.26.7

# 完整回归后，也可分别重跑两个探针。
pwsh -NoProfile -File scripts/smoke-gc.ps1
pwsh -NoProfile -File scripts/smoke-abi.ps1
```

GC 脚本会生成 NIR、构建程序、检查反汇编，并默认在两种模式下各运行 20 次。被测试的子程序必须输出 `42`、`7`、`43`，错误输出为空，正常退出；外层脚本还会输出自己的检查结果，所以整个终端显示不只这三个数字。[^gc-script]

ABI 脚本会故意制造错误库和错误布局。**预期的失败由测试脚本检查；只要失败原因正确，整套测试仍应成功结束。** 如果坏输入反而成功、正确对照失败，或失败原因不符合要求，脚本才判定测试失败。[^abi-script]

产物和本机记录位于 `.tynel/gc/`、`.tynel/abi/`。它们是实验生成物，不需要当作新的业务源文件提交。想了解某次结果，应看对应日志、配置与版本，而不只数终端里有几个 `PASS`。

---

回到最初那句进度汇报，现在可以完整地读成：

> 我们正在执行规格中的 T09。为了验证新编译路径能安全地处理一种最小对象，在 NIR 中增加了必须显式声明的 `probe.gc/1` 实验能力。GC 探针检查引用和数据经过回收与深栈调用后仍然正确；ABI 探针检查匹配的辅助库能使用、指定的不匹配组合会被拒绝。为什么采用这样的范围，写在 ADR-013；实际执行结果写在开发记录。这些证据还不能扩展成完整 TypeScript 对象与跨版本 ABI 支持。

以后再遇到陌生词，可以先问三个问题：**这是通用概念，还是项目自定义名称？它是在描述设计、代码，还是测试结果？当前证据究竟覆盖哪一种情况？** 这样读规格和进度，往往比一口气记住所有缩写更有效。
